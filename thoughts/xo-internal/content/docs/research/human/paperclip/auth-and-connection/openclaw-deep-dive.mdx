# OpenClaw Gateway Adapter — Deep Dive

This page explains how the `openclaw_gateway` adapter is **actually built** inside Paperclip — the real WebSocket protocol, the ED25519 device authentication, the connection handshake, the streaming event system, and every step of the `execute()` pipeline.

---

## What Makes OpenClaw Different From Every Other Adapter

Most Paperclip adapters spawn a **local CLI process** (claude, codex, gemini) or fire an **HTTP webhook** (http adapter). OpenClaw Gateway does neither — it opens a **persistent WebSocket connection** to a remote gateway server, authenticates via a cryptographic handshake, then sends agent work requests over that connection and streams results back in real time.

```

──────────────────                    ────────────

└──────────┘                         └──────────┘
    │ stdout                              │ JSON response
    ▼                                     ▼
```

## The Gateway Protocol (V3)

OpenClaw uses a custom WebSocket frame protocol with three frame types:

```
┌──────────────────────────────────────────────────────────────┐
│                  GATEWAY FRAME TYPES                          │
│                                                               │
│  REQUEST FRAME (client → gateway)                             │
│  ─────────────────────────────────                            │
│  { type: "req", id: "uuid", method: "agent", params: {...} } │
│                                                               │
│  RESPONSE FRAME (gateway → client)                            │
│  ──────────────────────────────────                           │
│  { type: "res", id: "uuid", ok: true, payload: {...} }       │
│  { type: "res", id: "uuid", ok: false,                       │
│    error: { code: "pairing_required", message: "..." } }     │
│                                                               │
│  EVENT FRAME (gateway → client, unsolicited)                  │
│  ────────────────────────────────────────────                 │
│  { type: "event", event: "connect.challenge",                 │
│    payload: { nonce: "abc123" }, seq: 1 }                     │
│  { type: "event", event: "agent",                             │
│    payload: { runId: "...", stream: "assistant",               │
│               data: { delta: "Hello..." } }, seq: 42 }        │
│                                                               │
└──────────────────────────────────────────────────────────────┘
```

## Device Authentication (ED25519 Protocol V3)

OpenClaw uses **cryptographic device authentication** — each Paperclip server proves its identity by signing a challenge nonce with an ED25519 private key.

```
┌──────────────────────────────────────────────────────────────────────┐
│                                                                      │
│  HOW DEVICE AUTH WORKS                                                │
│                                                                      │
│  Gateway sends nonce ──────────────────────────────────────┐         │
│                                                             │         │
│  Paperclip builds payload string (pipe-delimited):          │         │
│  ┌──────────────────────────────────────────────────────┐  │         │
│  │ v3 | deviceId | clientId | clientMode | role |       │  │         │
│  │ scopes | signedAtMs | authToken | nonce |            │  │         │
│  │ platform | deviceFamily                              │  │         │
│  └──────────────────────────────────────────────────────┘  │         │
│                         │                                   │         │
│                         ▼                                   │         │
│              ED25519 Sign with privateKeyPem                │         │
│                         │                                   │         │
│                         ▼                                   │         │
│              Base64URL encode (no padding)                   │         │
│                         │                                   │         │
│                         ▼                                   │         │
│  Send in connect request:                                    │         │
│  {                                                           │         │
│    device: {                                                 │         │
│      id: "device-uuid",                                     │         │
│      publicKey: "base64url-32-bytes",  ◀── raw public key   │         │
│      signature: "base64url-sig",       ◀── signed payload   │         │
│      signedAt: 1712150400000,          ◀── timestamp ms     │         │
│      nonce: "abc123"                   ◀── from challenge ──┘         │
│    }                                                                  │
│  }                                                                    │
│                                                                      │
│  Device identity sources:                                             │
│  ┌────────────────────────────────────────────────────────────┐      │

│  │   → Used for pre-paired devices                             │      │
│  │                                                             │      │

│  └────────────────────────────────────────────────────────────┘      │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

## Auto Device Pairing Flow

When a new device connects for the first time, the gateway requires **pairing approval**. The adapter can auto-approve this:

```
execute() attempt #1
    │
    │──── WebSocket connect ────▶ Gateway
    │◀──── ERROR: "pairing required" ────│
    │       (extractPairingRequestId)
    │
    ├── Is autoPairOnFirstConnect? YES
    ├── Has authToken or password? YES
    ├── Already attempted? NO
    │
    ▼
autoApproveDevicePairing()
    │
    │  1. Open NEW WebSocket (with "operator.pairing" scope)
    │  2. Connect with auth credentials
    │  3. If no requestId known:
    │     ├── REQ: "device.pair.list" → get pending requests
    │     └── Filter to matching deviceId or pick latest
    │  4. REQ: "device.pair.approve" { requestId }
    │  5. Close pairing WebSocket
    │
    ├── ok: true  → log success, RETRY execute (continue while loop)
    └── ok: false → log failure, return error result

execute() attempt #2 (after successful pairing)
    │
    │──── WebSocket connect ────▶ Gateway
    │◀──── RES: { ok: true } ──────│  ✓ Device now paired!
    │
    │──── REQ: "agent" ────────────▶ (normal flow continues)
    │
    ...
```

## Session Routing Strategies

OpenClaw sessions are keyed differently depending on the strategy:

```
┌─────────────────────────────────────────────────────────────────┐
│                   SESSION KEY STRATEGIES                          │
│                                                                  │
│  STRATEGY: "issue" (default)                                     │
│  ────────────────────────────                                    │
│  Key format: "paperclip:issue:{issueId}"                         │
│  Behavior:  Same agent + same task = same session                │
│             Different tasks get different sessions                │
│  Best for:  Most use cases — context per task                    │
│                                                                  │
│  STRATEGY: "fixed"                                               │
│  ────────────────                                                │
│  Key format: configuredSessionKey or "paperclip"                 │
│  Behavior:  ALL runs share ONE session                           │
│  Best for:  Agents with global context (CEO, monitor)            │
│                                                                  │
│  STRATEGY: "run"                                                 │
│  ───────────────                                                 │
│  Key format: "paperclip:run:{runId}"                             │
│  Behavior:  Every heartbeat gets a FRESH session                 │
│  Best for:  Stateless tasks, one-shot operations                 │
│                                                                  │
│  ┌──────────────────────────────────────────────────────┐       │
│  │                    EXAMPLE                            │       │
│  │                                                       │       │
│  │  Agent: CTO (claude)                                  │       │
│  │  Strategy: "issue"                                    │       │
│  │                                                       │       │
│  │  Heartbeat 1 (task_A):  session = "paperclip:issue:A" │       │
│  │  Heartbeat 2 (task_A):  session = "paperclip:issue:A" │ ← resume│
│  │  Heartbeat 3 (task_B):  session = "paperclip:issue:B" │ ← new  │
│  │  Heartbeat 4 (task_A):  session = "paperclip:issue:A" │ ← resume│
│  └──────────────────────────────────────────────────────┘       │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## Environment Test: probeGateway()

Before running agents, `testEnvironment()` validates the gateway is reachable:

```
testEnvironment(config)
    │
    ├── Check: url present?
    ├── Check: url valid? (ws:// or wss://)
    ├── Check: wss:// for remote hosts? (warn if ws:// to non-localhost)
    ├── Check: auth token present?
    │
    ├── probeGateway():
    │   │
    │   ├── Open WebSocket (3-second timeout)
    │   ├── Receive "connect.challenge" event
    │   ├── Send "connect" request with credentials
    │   │
    │   ├── Result: "ok"             → info: "Gateway authenticated"
    │   ├── Result: "challenge_only" → warn: "Connected but auth failed"
    │   └── Result: "failed"         → error: "Cannot reach gateway"
    │
    └── Return: { status: "pass"|"fail", checks: [...] }
```

## Complete Error Code Reference

| Error Code | When | Action |
|------------|------|--------|
| `openclaw_gateway_url_missing` | No `url` in config | Run fails immediately |
| `openclaw_gateway_url_invalid` | URL cannot be parsed | Run fails immediately |
| `openclaw_gateway_url_protocol` | URL is not `ws://` or `wss://` | Run fails immediately |
| `openclaw_gateway_agent_error` | Gateway returns error on "agent" request | Run fails |
| `openclaw_gateway_wait_timeout` | `agent.wait` times out | Run marked timedOut |
| `openclaw_gateway_wait_error` | `agent.wait` returns error | Run fails |
| `openclaw_gateway_wait_status_unexpected` | Unknown status from wait | Run fails |
| `openclaw_gateway_timeout` | Overall execution timeout | Run marked timedOut |
| `openclaw_gateway_pairing_required` | Device needs pairing | May auto-retry |
| `openclaw_gateway_request_failed` | WebSocket/network error | Run fails |

## Comparison: OpenClaw Gateway vs HTTP Adapter vs Process Adapter

```
┌──────────────────┬────────────────────┬──────────────────┬───────────────────┐

│ Connection       │ Persistent,        │ Fire-and-forget  │ Spawn + exit      │
│                  │ bidirectional      │ (or callback)    │                   │
│ Streaming        │ ✓ Real-time events │ ✗ (poll or       │ ✓ stdout pipe     │
│                  │                    │   callback)      │                   │
│ Authentication   │ ED25519 device     │ Bearer token /   │ Env vars          │
│                  │ auth + token       │ API key header   │ (ANTHROPIC_API_KEY│
```
