## 1. Understanding OpenClaw's Native Access Control

While OpenClaw doesn't ship with a formal RBAC system, it provides a powerful set of primitives that, when combined, offer a robust foundation for access control. The key is to think in terms of **agent isolation**.

### Multi-Agent Architecture

An "agent" in OpenClaw is a fully-scoped entity with its own workspace, state, and session store. This is the foundation of RBAC in OpenClaw.

| Component | Path | Description |
|---|---|---|
| **Workspace** | `~/.openclaw/agents/<agentId>/workspace` | Agent-specific files, persona, and skills. |
| **State Directory** | `~/.openclaw/agents/<agentId>/` | Auth profiles, model registry, and per-agent configs. |
| **Session Store** | `~/.openclaw/agents/<agentId>/sessions` | Isolated chat history and routing state. |

By creating different agents for different roles (e.g., `dev-agent`, `marketing-agent`), you can assign different capabilities and permissions to each.

### Per-Agent Configuration

OpenClaw's `openclaw.json` allows you to define per-agent access profiles, including tool policies and sandboxing.

```json
"agents": {
  "personal-assistant": {
    "sandbox": { "mode": "all" },
    "tools": { "policy": "allowlist", "allow": ["web.search", "calendar.read"] }
  },
  "devops-agent": {
    "sandbox": { "mode": "non-main" },
    "tools": { "policy": "allowlist", "allow": ["web.search", "browser", "exec"] }
  }
}
```

| Config | Setting | Description |
|---|---|---|
| **Sandboxing** | `sandbox.mode` | `off` (no sandbox), `non-main` (sandbox non-main sessions), `all` (sandbox everything). |
| **Tool Policy** | `tools.policy` | `allowlist` (only specified tools) or `denylist` (all except specified). |

### User and Session Management

- **DM Pairing (`dmPolicy`)**: `pairing` policy requires admin approval for new users.
- **Session Scoping (`session.dmScope`)**: `per-channel-peer` isolates conversations to prevent context leakage.
- **Channel Allowlists**: `allowFrom` lists restrict access to specific users or groups.

## 3. Integrating Third-Party RBAC Solutions

For enterprise-grade deployments, integrating a dedicated RBAC library is the way to go. **Casbin** is a powerful, open-source choice.

### Casbin: A Flexible RBAC Library

Casbin lets you define your access control model in a `model.conf` file and your policies in a `policy.csv` file. This separates your authorization logic from your application code, making it easy to manage and audit.

```
# model.conf
[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub, p.sub) && r.obj == p.obj && r.act == p.act
```

```
# policy.csv
p, marketing, /api/posts, read
p, developer, /api/posts, write
g, alice, developer
```

### Real-World Example: Sendbird's AI Agent RBAC

Sendbird uses a two-layer model for their AI agents:

| Layer | Definition | Scope |
|---|---|---|
| **Role** | A label for a job function (e.g., "AI Admin"). | Broad |
| **Permission Set** | Specific actions a user can perform (e.g., "view performance data"). | Granular |

This allows for a clear separation of duties and fine-grained control over agent capabilities.
